# 0020 — 提交历史右键「推送标签」动作

状态：已接受  
日期：2026-10-27

## 背景

0019 给提交历史的右键菜单加了「创建标签」，标签只落在本地。用户随后发现「推送当前分支」推不动这些标签：`git push` 只推分支，不推标签，所以本地建好标签后远端没有对应 ref（实测：`git push` 报 `Everything up-to-date`，`git ls-remote --tags --refs origin` 为空）。

同时「推送当前分支」按钮在本地标签存在但已推送当前分支上没有新提交时是禁用的（`hasPushableCommits` 要求 `ahead > 0`，决策 0009）。也就是说：用户最常见的路径——同步完分支再打一个发布标签——恰好落在按钮两端都够不着的位置，没有任何入口能把标签推上去。

## 决策

- 新增独立的「推送标签」动作，而不是改动「推送当前分支」的语义或门控：
  - 按钮禁用条件保持 `ahead > 0` 不变，不引入网络探测（`ls-remote`）来放宽它——那会让一个纯本地的门控依赖网络，离线时行为不可预测。
  - 提交历史右键菜单在已有标签处逐条列出「推送标签 <tag>」，与「创建标签」并列；一个提交有多个标签就逐条给出，避免再猜「推哪个」。
- 被否决的备选：
  - 「推送当前分支时顺带推送本地标签」——改变了用户按下的那个按钮的含义（一次网络写操作变成两种对象），且需要额外的 `--merged` 过滤、同名不同提交的处理和多远端跳过逻辑，失败面明显更大。
  - `git push --follow-tags`——只推注释标签（轻量标签永远不会被带上去），并且分支没有可推内容时整个 `push` 直接结束，解决不了本问题的主场景。
- 推送实现固定在 `src/git.ts` 的 `pushTag`：先 `rev-parse --verify refs/tags/<name>` 取本地对象 id，再 `ls-remote --refs <remote> refs/tags/<name>` 比对远端，相同则直接返回 `pushed: false` 不推送；不同或远端缺失时执行显式 refspec `git push <remote> refs/tags/<name>:refs/tags/<name>`。远端同名标签指向别处时由 git 自己拒绝（非快进），本动作永不 `--force`、永不注入加速前缀（决策 0018 的 `-c` 重写只适用于 fetch 侧）。
- 远端不猜：`resolvePushRemote` 依次取当前分支 upstream 的 remote、`remote.pushDefault`、仓库中唯一的 remote；多 remote 且无 upstream 时返回 400 并提示可用 `git config remote.pushDefault` 指定，而不是随机挑一个。
- 标签名不合法/不是本地标签返回 400，「已是最新」与「推送成功」在 UI 上区分提示（`src/client/locales.ts` 的 `panel.tagPushDone` / `panel.tagPushUpToDate`）。

## 影响

- 用户从提交历史就能把某个标签发布出去，不再依赖按钮门控或本地 ahead 状态；「推送当前分支」保持 0008/0009 的既有语义不变。
- 网络动作有两个（`ls-remote` 与 `push`），都使用 `NETWORK_TIMEOUT_MS`；本地 `rev-parse` 仍用默认预算。远端标签与本地同名同对象时不会产生多余的推送。
- 一次点击最多推送一个标签，不批量发布；想推多个标签需要逐个操作。这是刻意的：发布动作保持显式，避免把用户没打算发布的标签一起送出去。
- 远端已有同名标签但指向不同提交时，动作以 git 的错误信息失败（非快进），不做自动覆盖；需要覆盖时用户须自行决定是否 force。
