# 0044 — 镜像退为"读加速"，失败即回直连；SSH 远端显式提示

- 状态：已采纳（2026-11-03）
- 关联：0018（加速前缀只作用于读）、0041（预算与失败分类）、0042（IP 优选）、0043（代理通道）

## 背景

决策 0018 把镜像前缀限定在 fetch/update：镜像是应用层终结，只有 `upload-pack`，没有 `receive-pack`，写操作走镜像必然失败，而且会把推送内容交给第三方。这一条没有变。

但"只用于读"之后的语义还没有定义：镜像失败时怎么办。实测（2026-11-03）显示镜像不是可靠的，也不是恒定的：

- `gh-proxy.com` 上私有仓库直接回 `could not read Username`（它拿不到本地凭据，也不该拿到）；
- 镜像站会被限流、会改路径格式（0040 就是为裸路径失效改的）；
- `git.tangbai.cc` 两种格式都返回 repository not found。

在 0018 的写法里，这些都变成一次失败的 fetch——尽管直连当时完全可用。用户看到的是"加速开着，拉取失败"，而正确答案是"这次加速没成，直连再来一次"。

另一件事实：SSH 远端（`git@github.com:o/r.git`）不能使用任何 HTTP 通道——镜像前缀只重写 `https://github.com/`，`http.curloptResolve` 只影响 HTTP 解析，`http.proxy` 也只对 HTTP 生效。此前遇到这种情况会先探测直连失败、再逐个尝试通道，全部无效后才报错，用户只看到一句 `Could not read from remote repository.`。

## 决策

1. **镜像失败一律回直连一次**：`fetchAll` 里只要注入了 `-c url.<prefix>…insteadOf`，任何失败（含 401/403/5xx/超时）都先丢弃重写、用原始 URL 重试一次。读是幂等的，重试不会造成重复；镜像只是加速器，不是权威。
2. **回直连之后再走通道链**：直连也失败时，才按 0043 的链（代理 → IP 优选）继续。顺序是"镜像 → 直连 → 通道"，镜像永远不参与备用通道判定。
3. **通道重试时丢弃镜像重写**：换到 IP 优选/代理时命令 argv 用原始 URL；否则 `insteadOf` 会把 github.com 又改回镜像，pin 就落到了一个用不上的主机上。
4. **SSH 远端不探测通道，直接给建议**：`isSshEndpoint` 识别 `ssh://`、`user@host:path` 与 scp 风格写法；命中时 fetch/push 不再往下试通道，错误里追加一句"代理与 IP 优选只作用于 https 远端，可改用 https://github.com/<owner>/<repo>.git"。
5. **推送路径同样拦截**：`chooseChannel` 在探测失败后先判 SSH，避免为一条不可能成功的路径再付 10s 探测。

被否决的备选：

- 镜像失败后静默改用通道、跳过直连：直连是用户预期里那条路，跳过它会让"其实直接就能连"的场景多绕一圈。
- 自动把 SSH 远端改写成 HTTPS：改远端是用户的决定（ssh key、端口、主机别名都可能有意为之），插件只提示不改。
- 镜像失败只在 UI 提示、不自动重试：用户要的是"拉下来"，不是"知道镜像挂了"。

## 影响

- 开着加速的失败路径从"一次失败"变成"两次尝试"，最坏多一次 fetch 的时间（300s 预算内）；成功路径零变化。
- 私有仓库在镜像上原本 100% 失败，现在会自动落到直连，凭据也只发给 GitHub 本身。
- SSH 用户第一次遇到网络失败时就能看到可执行的建议，而不是三次探测后的通用错误。
- 新增诊断脚本 `scripts/probe-network.mjs`：对直连/镜像/代理/若干 IP 各跑一次真实 `ls-remote`，输出与 `/network-probe` 同格式的表格——用于复现问题，也是 0041"判据必须是真实 ls-remote"的操作化。
